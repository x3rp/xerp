# Spec 013 — notes (builder)

Branch `feat/013-master-data-rules`. No tester's test was changed; none is disputed.

## B-N1. The entity no longer refuses a partner without a role

`Partner.Replace` threw `ArgumentException` for a partner with neither role: a constant copy of 004/R15, and a
`500` once `partner.roleRequired` = `false` (AC-40). It is removed (AC-02: no check of 6.1 remains as a
constant); the rule is judged only in `PartnerValidation`, with the tenant's value. Two builder's unit tests
of spec 004 that pinned the throw were changed accordingly (`AddressAndPartnerRulesTests`). This is a sixth
kind of change to an earlier test, not among the five of AC-01.

## B-N2. Rule keys may carry a digit

`partner.addressLine1Required` and three others have a digit; the builder's unit test of 012 that held keys to
letters only (`^[a-z][A-Za-z]*\.[a-z][A-Za-z]*$`) now allows digits. ADR-0020 says "two lowerCamel segments"
and does not exclude them.

## B-N3. Where the rules are read, and the lock

Create and replace of the four masters read `IRules` once, before validation (validation needs the values),
and run every later stage inside `SerializedPerTenantAsync` — always, not only when a uniqueness rule is
`true`. A rule change that commits between that read and the lock is not seen by the write in flight; it
applies from the next operation (012/R13).

## B-N4. No migration

No index was added for the lookups of R12 and R15 (section 3 allows, does not require them): the lookups run
only when a uniqueness rule is `true` and scan the tenant's rows of one resource.

## B-N5. To T-Q2

All eight descriptions name `rule_list` and the new codes (`NAME_TAKEN` on all eight, `CODE_CHANGE_NOT_ALLOWED`
on the four update tools, `TAX_ID_TAKEN` on the two partner tools).

# Answers (architect, 2026-10-13, with review 013)

None of them changes a test or the code.

- **T-Q1.** Right: items 1 and 2 of AC-01, and nothing else was needed. No name or description of the 24 rules
  as built contains `partnerRequired`, so 012 AC-22 stands as it is.
- **T-Q2.** Both readings are met: the builder put `rule_list` and the new codes in all eight descriptions
  (B-N5). The spec's sentence stays ("where a description lists the tool's error codes"); the test's condition
  is the right one for it.
- **T-Q3.** Yes. Two role fields that are given and both `false` are values, so the role refusal is part of
  validation and is reported with every other invalid field, naming `partner.roleRequired`. Only a missing or
  wrong-typed role field is reported without the role refusal (004/R15, R8).
- **T-Q4.** All four assumptions are what R9, R12, R15, R16 and R13 mean: codes, names and tax ids are compared
  after normalisation (so `" AB1 "` is the stored `AB1`, `" HR123 "` collides with `HR123`, a blank tax id is
  none); the order on a replace is code change -> `CODE_TAKEN` -> `NAME_TAKEN` -> `TAX_ID_TAKEN`; R13 holds
  for replaces as for creates.
- **T-Q5.** Noted. The orchestrator runs the suite before the merge (review 013, merge note).

- **B-N1. Accepted.** The entity's throw was a constant copy of a rule that is now a tenant's; with
  `partner.roleRequired` = `false` it would have been a `500`. Removing it is what AC-02 asks. The two changed
  assertions are the builder's own unit tests of spec 004, they pinned the constant and not a behaviour
  through the API, and their replacement asserts the rule as a function of its boolean. AC-01 of the spec now
  lists this as item 6.
- **B-N2. Accepted.** A segment of a key is lowerCamel and may contain digits; it starts with a lower-case
  letter. ADR-0020 (decision 2) says so now.
- **B-N3. Accepted.** Reading the rules before validation and taking the lock afterwards is R4 and 012/R13: a
  rule change that commits while a write is in flight applies from the next operation. The lock is taken
  always, which the spec's note offers as the simplest correct form. Two writes that both read `nameUnique` =
  `true` are serialized, so R13 holds.
- **B-N4. Accepted.** Section 3 allows the indexes and does not require them. Recorded as open item 013/1
  (performance only, when a tenant with a uniqueness rule on has many records).
- **B-N5.** See T-Q2.
