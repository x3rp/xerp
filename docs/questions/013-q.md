## T-Q2. Section 5, descriptions — what is asserted

The spec says the eight descriptions mention `rule_list`, and that the new codes are added "where a description
lists the tool's error codes". The test asserts `rule_list` in all eight unconditionally, and the new codes only
in a description that already lists `CODE_TAKEN`. Is that the intended reading, or must all eight list the codes?

## T-Q3. A partner with neither role together with other invalid fields (R8, R18)

`AC22_R18` sends both roles `false` (given, not missing), a 201-character name and `"countryCode": "Croatia"`
and expects all four keys in one response with `rules` = `partner.roleRequired`, `fields`
`["isCustomer", "isSupplier"]` — as 004 AC reports the role keys together with `code` and `name`. Only a
*missing or wrong-typed* role field is expected alone and without `rules` (AC-40).

## T-Q4. Assumptions taken from R9, R12, R15 beyond the literal ACs

  `partner.codeChangeable` = `false` as well, `CODE_CHANGE_NOT_ALLOWED` (AC-63).
- R13 for replaces: six parallel replaces giving one name to six partners -> exactly one `200` (second AC-64
  test).

# Spec 013 — notes (builder)

Branch `feat/013-master-data-rules`. No tester's test was changed; none is disputed.

## B-N1. The entity no longer refuses a partner without a role

`Partner.Replace` threw `ArgumentException` for a partner with neither role: a constant copy of 004/R15, and a
`500` once `partner.roleRequired` = `false` (AC-40). It is removed (AC-02: no check of 6.1 remains as a
constant); the rule is judged only in `PartnerValidation`, with the tenant's value. Two builder's unit tests
of spec 004 that pinned the throw were changed accordingly (`AddressAndPartnerRulesTests`). This is a sixth
kind of change to an earlier test, not among the five of AC-01.

## B-N2. Rule keys may carry a digit

`partner.addressLine1Required` and three others have a digit; the builder's unit test of 012 that held keys to
letters only (`^[a-z][A-Za-z]*\.[a-z][A-Za-z]*$`) now allows digits. ADR-0020 says "two lowerCamel segments"
and does not exclude them.

## B-N3. Where the rules are read, and the lock

Create and replace of the four masters read `IRules` once, before validation (validation needs the values),
and run every later stage inside `SerializedPerTenantAsync` — always, not only when a uniqueness rule is
`true`. A rule change that commits between that read and the lock is not seen by the write in flight; it
applies from the next operation (012/R13).

## B-N4. No migration

No index was added for the lookups of R12 and R15 (section 3 allows, does not require them): the lookups run
only when a uniqueness rule is `true` and scan the tenant's rows of one resource.

## B-N5. To T-Q2

All eight descriptions name `rule_list` and the new codes (`NAME_TAKEN` on all eight, `CODE_CHANGE_NOT_ALLOWED`
on the four update tools, `TAX_ID_TAKEN` on the two partner tools).
