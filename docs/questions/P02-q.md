# Spec P02 — tester's questions

Q1. `whoami` and a `pos` key (R32, R33). `GET /whoami` is not on the allow-list of R32, so read literally a `pos`
key gets `403` there and `tools/list` for a `pos` key does not contain `whoami`. A till (or an agent at the till)
would normally want to know its tenant and key. The tests leave it open: AC-52 compares the `pos` tool list with
`whoami` removed from both sides, and no test calls `GET /whoami` with a `pos` key. Is `whoami` on the list?

Q2. Annotations of `pos_operator_set_pin`, `pos_session_start`, `pos_session_end` and `pos_authorize` are not given
by section 5 (end is repeatable, authorize writes only PIN counters). The tests pin the annotations of the ten master
tools only (as P01) and the metadata (description, closed schema, properties, `required`) of all sixteen.

Q3. `GET /api-keys?scope=x`: the spec adds the filter but not its refusal; by analogy with `actorType=x` it would be
`400`, key `scope`. Not tested.

Q4. AC-53: the Session representation (4.C) has no `createdBy`, so the test checks attribution through `apiKeyId`
and the `CreatedBy` column of `PosSessions` read directly (as section 10 allows for time-dependent criteria).

Q5. `pos_operator_create` input schema: the tests expect `roleId` nullable and outside `required` (it is judged by
`posOperator.roleRequired`, as the 013 rule-required fields), `pin` required.

## Builder's notes

B-1. **AC-60 contradicts the order of checks** (left failing, test not edited).
`AC60_Y_cannot_read_replace_delete_or_reference_X_s_role_operator_or_session_and_creates_the_same_codes` replaces X's
operator from tenant Y with `roleId: null` and expects `404`. In Y `posOperator.roleRequired` is at its default `true`,
so the body fails validation, and the order of checks of every replace is validation -> exists (013/R10; P02/R1
inherits it; R3 makes the refusal `400 VALIDATION_FAILED` with `rules`). The builder answers `400`. The test would
pass with a body that is valid in Y (for example `roleId` naming a role of Y, or the rule set to `false` first);
the one-line fix is in the test, not in the order. Architect: please decide.

Answers to the tester's questions, as built:
- Q1 `whoami`: not on the allow-list (read literally): a `pos` key gets `403` on `GET /whoami` and does not see the
  tool. Adding it is one row in `PosAllowList.Reads` if the architect wants it.
- Q2 annotations: `pos_operator_set_pin` Update, `pos_session_start` Create, `pos_session_end` Repeatable,
  `pos_authorize` Read (it writes only the approver's PIN counters).
- Q3 `GET /api-keys?scope=x` -> `400`, key `scope`, as `actorType=x`.
- Q5 `pos_operator_create`: `roleId` nullable, not in `required`; `pin` required. An omitted `roleId` on create is
  null (then judged by the rule); on replace `roleId` must be present (a UUID or null), as 004/R7.

Builder's decisions:
- Sign-in (session start and approver) runs under the tenant's lock and additionally locks the operator's row
  (`SELECT ... FOR UPDATE`); the failed-attempt increment is saved and committed in that transaction although the
  request is refused. One lock order everywhere (tenant, then operator) avoids deadlocks between sign-ins, set PIN
  and the device rules.
- PIN hash: PBKDF2-HMAC-SHA256, 100 000 iterations, 16-byte random salt, stored as `pbkdf2-sha256$iter$salt$hash`.
  For a cause that never reaches the PIN (unknown code, inactive, locked) one verification against a fixed dummy
  hash is run (S2).
- A success resets `FailedPinAttempts` only (R12); a past `lockedUntil` stays visible until the next set PIN.
- The allow-list is one table (`Application/Pos/PosAllowList.cs`: method, route template, tool) read by
  `ApiV1Middleware` (after authentication, before the endpoint) and by the MCP list and call handlers. It needs a
  matched endpoint, so an unknown path stays `404`.
- `JsonBody` maps a JSON error at `$.a.b` to the key `a.b` (it mapped only `$.a`, `$.a[i]` and `$.a[i].b`), so a
  wrong member of `rights` answers key `rights.<member>` (R2).
- `CodedMasterOperations` (P01) gained four virtual hooks (validation with the tenant's rules, references,
  work in the replace transaction, preparation of representations); the P01 masters do not override them.
