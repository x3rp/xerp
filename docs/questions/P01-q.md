# Spec P01 — questions of the tester

Tests: branch `tests/P01-sales-master-data`. Each point says what the tests assume until the architect answers.

## T-1. Key of `errors` for an unknown property

AC-21 and AC-43 say an unknown property is refused "with the key" / "its key". Specs 001–013 tests never pinned
that key (they only assert `400 VALIDATION_FAILED`). **Assumed:** the key is the property's own name
(`"foo": 1` -> `errors.foo`), and it is the only key.

## T-2. `required` of `article_sales_data_set` and the annotations of the new tools

Section 5 gives `categoryId: uuid|null`, `salesPrice: number|null` and R8 says all three members must be present.
**Assumed:** all four arguments are in `required` of the input schema (nullable, but not optional), and the tool has
the annotations of `article_unit_set` ("update": not read-only, destructive, idempotent). The fifteen master tools
are pinned as the `uom_*` tools are; `<m>_update` requires every field of the replace body.

## T-3. Tool descriptions

Section 5: "naming its error codes and, where rules judge it, `rule_list` with the group". **Assumed (pinned):**
the descriptions of `<m>_create` / `<m>_update` contain `rule_list`, the group (`articleCategory`, `taxRate`,
`paymentMethod`) and `NAME_TAKEN`; `article_sales_data_set` and `article_barcode_create` contain `rule_list` and
`article`; `article_barcode_create` contains `BARCODE_TAKEN`; `article_sales_data_set` contains "tax" and "includ"
(for "includes tax" / "tax-inclusive"). If the wording is meant to be free, say so and I drop the "includ" check.

## T-4. A barcode that is not a JSON string, or only spaces

6.2 defines the form of a barcode but not the wrong type. **Assumed:** `"barcode": 123` and `"barcode": "   "`
are `400` with the key `barcode` (as `""` in E8).

## T-5. NAME_TAKEN on a replace of the three masters

AC-28 lists only creates; 6.1 says "a create or replace". **Assumed:** a replace that takes another record's name
is refused as well (tested once per master).

## T-6. Earlier tests changed (AC-01)

Only what AC-01 allows: the rule count 30 -> 40 and the literal inventory (`RuleRegistryTests`, `Rules.All`,
`Rules.Default`), group `article` 3 -> 7, the tool count 62 -> 84 and the literal tool list (`McpToolListTests`).
No rule search of the earlier tests matches a new key, so item (4) needed no change. Not run against an
implementation yet: if another earlier test fails after the build, it comes here first.

# Spec P01 — notes of the builder

## B-1. AC-81 test expects one refused field where the spec gives two (the only failing test)

`SalesRuleIsolationAndMcpTests.AC81_T3_The_ten_values_of_one_tenant_change_nothing_for_another`, line 220: after
`SalesRules.SetAllToOtherAsync(x)` tenant X has `article.categoryRequired` **and** `article.taxRateRequired` =
`true`. The test then sends `{ categoryId: null, taxRateIds: [], salesPrice: 1 }` and asserts that `errors` has
exactly the key `categoryId`. By R10 ("`categoryId: null`, `taxRateIds: []` ... is refused ..., each naming its
rule, reported with every other invalid field") the answer is `400` with keys `categoryId` and `taxRateIds` and two
elements in `rules` — which is what the implementation returns. **Not changed:** the test (it is the tester's) and
the behaviour (it is the spec's). Fix on the tester's side: send one tax rate in that body, or expect both keys.
Everything else in the test passes up to that line; the lines after it were not reached.

## B-2. Answers the implementation gives to T-1..T-5 (all as the tester assumed)

T-1 the key is the property's own name. T-2 all four arguments of `article_sales_data_set` are `required`; the
tool is an "update". T-3 the descriptions carry the pinned words. T-4 `123` and `"   "` are `400`, key `barcode`.
T-5 a replace that takes another record's name is refused with `NAME_TAKEN`.

## B-3. Decisions the spec left to the builder

- Deletes of the three masters run under the tenant lock (as a Set of sales data does), so S2's race is settled
  by construction; the foreign key stays the authority behind it.
- `ArticleBarcodes.Barcode` has collation `C`: equality is exact and the list order is ordinal (R19) in SQL.
- `GET /article-barcodes?barcode=` with a whitespace-only value is `400`, key `barcode` (it is not a barcode);
  an empty value is an absent filter, as every query parameter.
- `RuleRegistry.Masters` still holds the four masters of spec 013 (a unit test pins their 22 rules); the three
  new ones are `RuleRegistry.SalesMasters`, built by the same `Master(...)`.
- Earlier builder unit tests changed, as AC-01 allows: `ConfigurableRuleTests` (literal list 30 -> 40) and
  `McpToolTests` (tool count 62 -> 84).

# Spec P01 — answers of the architect (2026-10-16)

Answered on `main` after review P01 (`docs/reviews/P01.md`). This file on `main` supersedes the branch's copy
at the merge (the branch's text is kept above, unchanged).

- **T-1. Yes.** An unknown property is refused with its own name as the key (`"foo": 1` -> `errors.foo`), and
  it is the only key when it is the only fault (I9). This is now the pinned reading for every spec.
- **T-2. Yes.** All four arguments of `article_sales_data_set` are in `required` (nullable, not optional: R8),
  and the tool is an "update" as `article_unit_set` is. The fifteen master tools are pinned as the `uom_*`
  tools; `<m>_update` requires every field of the replace body.
- **T-3. Yes, keep every pinned word, "includ" included.** Section 5 requires the sentence "`salesPrice`
  includes tax" in that description; pinning it is pinning the spec, not the wording around it.
- **T-4. Yes.** `"barcode": 123` is a wrong type and `"   "` is empty after trimming: both `400`, key
  `barcode`, no `rules` (I9, 6.2, E8).
- **T-5. Yes.** 6.1 says "a create or replace"; AC-28 lists creates only as examples. A replace that takes
  another record's name is refused by (`NAME_TAKEN`, `<m>.nameUnique`, `true`), as 013/R12 for every master.
- **T-6. Noted and confirmed.** The changed earlier tests are exactly AC-01 items 1–3 (renaming 013's
  `AC13_Still_62_tools…` to a count-neutral name is part of item 3). No other earlier test may change.

- **B-1. The test is wrong; the code is right.** R10 and E5 say a required-rule refusal is reported with every
  other invalid field, each naming its rule. In AC-81, X has all three required rules `true`, so the body
  `{ categoryId: null, taxRateIds: [], salesPrice: 1 }` lacks two required members and the answer is `400`
  with keys `categoryId` and `taxRateIds` and two elements in `rules`. The test asserts one key. The point of
  that line is only "X is judged by X's values", so the body must lack exactly one member.
  **Correction the tester makes** in `tests/Xerp.IntegrationTests/SalesRuleIsolationAndMcpTests.cs`,
  `AC81_T3_The_ten_values_of_one_tenant_change_nothing_for_another`, replace the line

  ```csharp
  await MasterRules.RequiredAsync(SalesData.PutAsync(x.Http, ofX, SalesData.Body(null, [], 1m)), SalesRules.CategoryRequired, "categoryId");
  ```

  with

  ```csharp
  var vatOfX = await x.TaxRateAsync("VAT25");
  await MasterRules.RequiredAsync(SalesData.PutAsync(x.Http, ofX, SalesData.Body(null, [vatOfX.Id()], 1m)), SalesRules.CategoryRequired, "categoryId");
  ```

  Nothing else in the test changes. (X has `taxRate.nameUnique` = `true`; the one tax rate `VAT VAT25` collides
  with nothing.) The builder changes nothing.
- **B-2. Confirmed.** Each of the five is what T-1..T-5 are answered with above.
- **B-3. All accepted.**
  - Deletes of the three masters under the tenant lock: the simplest form of S2; the foreign key stays the
    authority, and its violation maps to `IN_USE` / `REFERENCE_NOT_FOUND` as S2 says.
  - Collation `C` on `ArticleBarcodes.Barcode`: exact equality and ordinal order in SQL are what 6.2 and R19
    say. It is storage, not contract.
  - `GET /article-barcodes?barcode=` with whitespace only -> `400`, key `barcode`; empty -> absent filter.
    Right: whitespace only is not a barcode (as T-4 for a create), and an empty query value is absent for
    every list.
  - `RuleRegistry.SalesMasters` beside `Masters`: accepted; both are built by `Master(...)`, so AC-02 ("no
    copy") holds.
  - Builder unit tests `ConfigurableRuleTests` (30 -> 40) and `McpToolTests` (62 -> 84): AC-01 items 1 and 3.
