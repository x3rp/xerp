## What was checked and found right

Registry and rules (6.1, AC-02, AC-10)
- Ten new definitions: three `MasterRuleSet`s from the same `Master(...)` of spec 013 (`SalesMasters`), three
  required rules from one `SalesDataRequired(...)` builder, and `article.barcodeUnique` (default `true`).
  `All` is 40, ordered by key. Names and descriptions say what `true` and `false` do and name the tool.
- Every decision is a boolean through `IRules` passed to a Domain function: `MasterDataRules.RequiredValueMissing`,
  `SalesDataRules.BarcodeTakenByAnotherArticle` (over `MasterDataRules.Taken`); code change and name check
  are `MasterWriteChecks` of 013, not copies. `Api` reads no rule.
- The three required rules are one table (`SalesDataRequiredFields`) through `RequiredFields.CheckValue`, as
  the builder's note asked — no three branches. Each member is judged only where it has no other error, so E5
  gives `categoryId` (rule) and `salesPrice` (form), one element in `rules`; B-1's body gives two.
- Rules are read once per operation before validation; the writes run under `SerializedPerTenantAsync`
  (013/R13, R18).

Masters (4.A, R1–R6)
- `CodedMasterOperations<…>` is written once for the three resources; order of checks on replace is
  exists -> code change -> `CODE_TAKEN` -> `NAME_TAKEN` (013/R16). `CODE_TAKEN` from the unique index on
  `(TenantId, CodeLower)` under a race is translated.
- `rate`: 0–100, ≤ 4 decimals, normalised (`25.0000` -> `25`), `numeric(7,4)`. `kind`: exact, lower case,
  four values, stored as text; `?kind=` empty is absent, unknown `400`.
- `IN_USE`: a category counted in `ArticleSalesData`, a tax rate in `ArticleTaxRates`, also of inactive
  articles (no article filter); payment methods always deletable. A racing FK violation maps to `IN_USE`.
- No index on names (013 §3).

Sales data (4.B, R7–R15)
- Missing property vs `null` is tracked (`TrackedInput`), so R8 distinguishes "absent" from "null".
- R9: more than four -> `taxRateIds`; malformed or repeated element -> `taxRateIds[i]`.
- R11: validation -> article (`404`, active or inactive, R7) -> category -> each tax rate in order, first
  failure alone; `alreadyAssigned` keeps an inactive category / tax rate the article already has (E4).
- Set replaces the row and the links in one `SaveChanges` under the tenant lock; FK violation after a race
  is answered as `404` / `REFERENCE_NOT_FOUND` with the right key (S2). The article's `updatedAt` is not
  touched (R12).
- List: one item per article, filtered (`search`, `isActive`, `categoryId`, `taxRateId`, `priced`) and paged
  in SQL, then three queries for the page (R13; the builder note's "not in memory").
- `salesPrice` `numeric(15,6)`; 0 is a price. Embedded summaries are read live (R15).
- Article delete removes links, sales data and barcodes in the same transaction; none counts for `IN_USE`
  (R14).

Barcodes (4.B, R16–R21)
- Trim, then 1–50 characters U+0021–U+007E; stored as sent otherwise; collation `C`.
- Order: validation -> article reference -> same article (invariant, no `rules`; unique index
  `(TenantId, ArticleId, Barcode)` is its authority under a race) -> other article only when the rule is
  `true` (with `rules`). `BARCODE_TAKEN` is `409` and repeats only the sent barcode (R21).
- Lookup exact, `barcode` then article code; non-unique index `(TenantId, Barcode)`; no cross-article unique
  index (the rule).

Data, isolation, MCP (3, 8, 5)
- Six tables, all `ITenantOwned` (global filter), every FK composite with `TenantId`, restrict; one migration,
  no existing table changed. No `IgnoreQueryFilters()` added.
- 22 tools, 84 in all; `article_sales_data_set` requires all four arguments, says `salesPrice` **includes
  tax**, and names `rule_list` with group `article`; master create/update name `rule_list`, the group and
  `NAME_TAKEN`; `article_barcode_create` names `BARCODE_TAKEN` and the rule. Route `/articles/sales-data` is
  literal and `/articles/{id:guid}` is constrained.
- `Problems.cs` maps `BARCODE_TAKEN` to `409`.
