## What was checked and found right

Registry (R1, AC-10–AC-12)
- `RuleRegistry` has 30 definitions: the six of 012, `partner.roleRequired`, `partner.taxIdUnique`, and per
  master a `MasterRuleSet` (`codeChangeable`, `nameUnique`, a table field -> `…Required` rule): 2 + 3 + 9 + 8.
  Keys and defaults equal the list of AC-10 (also pinned literally by the builder's unit test). The
  definitions are static fields initialised in order of text before `Masters` and `All`; `AddressFields` is a
  property, so nothing is read before it exists.
- No table, column, migration, route or tool was added; `Rules/`, `IRules`, the rule operations and the MCP
  error mapping are untouched. `Problems.cs` maps the three new codes to `409`.

Decisions are functions of a boolean (AC-02, AC-03)
- `MasterDataRules.RequiredFieldMissing`, `CodeChangeRefused`, `Taken` and `PartnerRules.RoleMissing` are pure
  Domain functions of the values and the rule's value. The operations read `IRules` once per write; `Api`
  reads no rule; no check of 6.1 remains as a constant — the entity's throw for a partner without a role is
  gone (B-N1).

Required fields (R5–R7, R17, R18, E1–E3)
- `RequiredFields.Check` is one table lookup per optional field, on the **normalised** value (omitted, `null`,
  empty and blank are `null`), and skips a field that already has an error. So a replace body without the
  property, and a value in a wrong form (`"countryCode": "Croatia"`), keep their invariant's refusal without
  `rules` whatever the rule's value (R6, AC-23).
- `ValidationErrors.Add(field, message, rule, value)` records which rule refused which field; `ToError` adds
  one `rules` element per rule with exactly its fields, ordered by its first field in `errors` (R18, E3).
  A response no rule refused has no `rules`.

`partner.roleRequired` (R8)
- Judged only when both role fields are well-formed, as 004/R15; both keys are attributed to the rule. With
  `false` the partner is saved on create and replace; the role checks of orders and documents are untouched.

Code change (R9–R11)
- Ordinal comparison of the stored and the normalised new code; on replace only; placed immediately before
  `CODE_TAKEN` in all four masters, after `404` (and after the frozen fields and the base unit of an article,
  and `DEFAULT_WAREHOUSE` of a warehouse, which stay where they were).

Uniqueness (R12–R16, T3, S2)
- `MasterWriteChecks.NameAsync` and the tax-id lookup run only with the rule `true`, on the tenant-filtered
  set (no `IgnoreQueryFilters`), excluding the record being replaced, with the same `lower()` on both sides
  as the code lookup; inactive records count; a `null` tax id is never looked up. Order: `CODE_TAKEN` ->
  `NAME_TAKEN` -> `TAX_ID_TAKEN`, each alone.
- `detail` and `errors` of the two errors repeat only the value the caller sent.
- Create and replace of all four masters run the checks and the write inside `SerializedPerTenantAsync`
  (a row lock on the tenant in one transaction), so of parallel writes with the rule `true` one wins (R13).
  The `UniqueConstraintViolation` and `DbUpdateConcurrency` translations stay around the lock.

MCP (section 5)
- No tool and no schema changed. The eight descriptions name `rule_list` with the master's group and the new
  codes (`NAME_TAKEN` on eight, `CODE_CHANGE_NOT_ALLOWED` on the four updates, `TAX_ID_TAKEN` on the two
  partner tools); the partner tools no longer state the role and the tax id as fixed facts.
