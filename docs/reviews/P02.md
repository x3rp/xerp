## What was checked and found right

Registry and rules (6.1, AC-02, AC-10)
- Eight definitions: two `MasterRuleSet`s from `RuleRegistry.Master(...)` (`posRole`, `posOperator`), the
  required rule through the same `RequiredFields` table mechanism as P01 (`PosOperatorRequiredFields`), and
  the three `pos.*` rules with defaults `true`. Names and descriptions say what each value does and name the
  tools. 48 in `All`, ordinal order.
- Every decision is a boolean read once per operation through `IRules`: `roleRequired` in
  `PosValidation.Operator`, approval in `PosRules.BeforeApproverSignIn`/`Decide` (pure Domain), the two device
  rules in `StartAsync`. Rights are columns of `PosRoles`, not rules (ADR-0022/7). `Api` reads no rule.
- The refusal of the approval rule carries `rules` (`RefusedBy`), key `approverCode`; "approver is the
  operator" carries none (R20 step 5).
- Lockout numbers, PIN form and session lifetime are constants in `PosRules`, as 6.2 makes them platform
  invariants (I2), not tenant rules.

Roles and operators (4.A, 4.B, R1–R8)
- Both are `CodedMasterOperations` (P01); the four new virtual hooks default to no-ops, so the P01 masters are
  unchanged. Order on replace: validation -> exists -> references -> code change -> `CODE_TAKEN` -> `NAME_TAKEN`.
- `rights`: all seven required, wrong types and unknown members refused by the strict binding; `JsonBody` now
  maps `$.rights.refund` to `rights.refund` (R2). The regex widening keeps the earlier forms.
- `roleId`: tracked "given" (`TrackedInput`), required on replace, nullable; unknown -> `REFERENCE_NOT_FOUND`,
  inactive newly assigned -> `REFERENCE_INACTIVE`, kept inactive role allowed (ADR-0008 via `ReferenceCheck`).
- A replace body with `pin` is an unknown property (`ReplacePosOperatorInput` has no `Pin`).
- Set PIN (R5): hash computed before the lock, operator row locked, counters cleared, `lockedUntil` null,
  sessions ended, attributed (`Touch`). Deactivation ends sessions in the replace transaction (R6); a role
  change ends none.
- `IN_USE`: role named by any operator; operator with any session. Deletes run under the tenant lock, as do
  sign-ins, so a delete cannot race a sign-in; the composite FK is the backstop (`ForeignKeyViolationException`
  -> `OPERATOR_SIGN_IN_FAILED`, S3).

Sessions and authorize (4.C, R10–R22)
- One `PosSignIn.VerifyAsync` for a session and for an approver: lookup by `CodeLower` in the tenant, row lock
  (`SELECT … FOR UPDATE` with `TenantId` in the predicate), tracked copy re-read after the lock; inactive,
  locked and unknown all run one dummy verification (S2) and count nothing; a wrong PIN increments and is saved
  inside the transaction that is committed although the request is refused (R11). One answer, one `detail`,
  key `pin` / `approverPin`, never the PIN.
- Status and `endedAt` computed (R14); `End` changes only an active session (R15); `PosSessions.EndAsync`
  writes only active rows. Get, list, end and authorize use `OwnSessions()` (key-bound, R13); another key's
  session is `404` / `REFERENCE_NOT_FOUND`.
- Rights read live from the current role, an inactive role gives `role: null` and all `false` (R14, E5).
- Authorize follows R20 in order; with an approver the approver is always checked (E8); self-approval by code
  in any case is refused before sign-in, so nothing is counted (E7); success writes only the approver's count
  reset (R21); no session for the approver.

POS-only keys (4.D, R30–R36)
- `scope`: omitted -> `full`, `null` or another value -> `400` key `scope` (tracked input); list filter
  validated; `Scope` on the record, read by `ApiKeyLookup`; migration adds the column with default `'full'`.
- One allow-list table (`PosAllowList`) read by `ApiV1Middleware` (after authentication, before the endpoint
  and its validation, only for a matched endpoint and method, so unknown paths stay `404` — E9, E10) and by
  the MCP list and call handlers (R33). No `if (scope == pos)` in endpoints.
- A `pos` key cannot reach `/api-keys` or `PUT /rules/{key}` (not on the list); `/pos/` writes except
  managing roles and operators are allowed (R32).

Tenant isolation and security
- All new tables are tenant-owned with composite FKs (`TenantId`, `Id`); no new `IgnoreQueryFilters()`; the
  only raw SQL is the row lock, parameterised and tenant-scoped.
- PINs: PBKDF2-HMAC-SHA256, 100 000 iterations, 16-byte salt, constant-time compare, self-describing format.
  No DTO, tool result or error carries the PIN or the hash; `JsonBody` does not echo exception texts; the MCP
  error log logs the tool name, not its arguments (S1).
- HTTP/MCP parity: 16 tools over the same Application operations, inputs and errors as HTTP.

## Non-blocking

- **P02/1 — sign-ins run under the tenant lock with the slow hash inside it.** Every sign-in and every
  authorize with an approver of a tenant is serialised behind one PBKDF2 verification (tens of ms), and so is
  every other write that takes the tenant lock. Correct and simple for P02. When P05a puts bill writes under the
  same lock, measure it; the fix then is to verify the PIN under the operator's row lock only (the device
  rules and the session insert need the tenant lock, the PIN check does not). Record for the P05a spec.
- `RequestActor.Set` assigns `Scope` before the "actor cannot change" guard; harmless (the guard throws), but
  the assignment belongs after it.
